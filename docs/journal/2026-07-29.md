# Diario de desarrollo — 2026-07-29

## Módulo 28: gestión de clientes desde la UI

- Se habilitó el alta de clientes desde `/app/` para operadores con la
  capacidad `customers.write`.
- Se añadió edición de nombre, teléfonos, correo y notas mediante un formulario
  accesible y adaptable a pantallas pequeñas.
- Las acciones de escritura permanecen ocultas para cuentas sin permiso.
- La interfaz compara el formulario con el registro original y evita enviar
  actualizaciones vacías.
- Toda modificación exige un motivo operativo.
- El backend registra auditoría inmutable para altas y ediciones, con valores
  anteriores y posteriores.
- Los errores de validación de la API se traducen en mensajes visibles dentro
  del formulario.
- No se añadieron dependencias ni cambios de base de datos.
- Las ciento cuarenta y seis pruebas están aprobadas, incluida la protección
  contra actualizaciones sin cambios reales.

## Módulo 29: alta de servicios desde la UI

- Se añadió el formulario de alta para cuentas con `services.write`.
- El operador selecciona un titular existente y un plan activo en lugar de
  capturar nombre o precio libremente.
- El backend valida que `plan_id`, nombre y precio mensual coincidan con el
  catálogo vigente.
- Se conservó compatibilidad de lectura y creación programática para servicios
  históricos que todavía no tienen `plan_id`.
- Cada alta genera titular inicial, evento de registro y auditoría inmutable.
- Los servicios nuevos permanecen pendientes; el formulario no omite el flujo
  de instalación ni activa conexiones.
- La UI exige código AMR válido, domicilio, día de pago, tolerancia y motivo.
- No se requirió migración porque `services.plan_id` ya existía.
- Las ciento cuarenta y siete pruebas están aprobadas.

## Módulo 30: recepción segura de pagos desde la UI

- Se añadió el formulario de recepción para cuentas con `billing.write`.
- El operador selecciona al cliente y, de forma opcional, uno de sus servicios
  visibles; también registra monto, fecha, medio y referencias operativas.
- Todo pago creado desde la interfaz conserva el estado `pending`.
- La pantalla aclara que registrar el pago no reduce deuda y mantiene fuera de
  este flujo la verificación y la aplicación.
- La referencia de almacenamiento del comprobante permanece en la base de
  datos, pero se retiró de las respuestas públicas.
- La API expone únicamente `has_proof` para indicar si existe evidencia.
- Cada recepción continúa generando evento de estado y auditoría inmutable.
- No se requirió migración de base de datos.
- Las ciento cuarenta y ocho pruebas están aprobadas y Alembic confirma que el
  esquema permanece sincronizado.

## Módulo 31: aprobación y aplicación de pagos desde la UI

- Se añadieron acciones visibles únicamente para cuentas con
  `billing.approve`.
- Los pagos pendientes pueden verificarse, rechazarse o cancelarse sin borrar
  su historial.
- La interfaz exige explicación cuando el monto confirmado difiere del
  declarado y para toda decisión de rechazo o cancelación.
- Verificar un pago no reduce deuda; el operador recibe una advertencia clara
  de que todavía debe aplicarlo.
- Los pagos verificados y no aplicados ofrecen una segunda confirmación para
  distribuir el monto entre los cargos abiertos más antiguos.
- La interfaz informa cuánto se aplicó a deuda y cuánto se convirtió en saldo a
  favor.
- Se corrigió la política del backend para que aplicar un pago también exija
  `billing.approve`, cerrando un posible atajo mediante `billing.write`.
- No se requirió migración de base de datos.
- Las ciento cuarenta y nueve pruebas están aprobadas y Alembic no detecta
  cambios pendientes.

## Módulo 32: estado de cuenta por cliente

- Se añadió un resumen autoritativo por cliente con deuda total, deuda vencida,

  y estado sin permitir mutaciones.
- Las fechas sin hora se interpretan como fechas locales para evitar que el
  navegador muestre el día anterior por conversión de zona horaria.
- No se requirió migración de base de datos.
- Las ciento cuarenta y nueve pruebas continúan aprobadas y Alembic confirma

## Módulo 33: catálogo de planes desde la UI

- Se añadió una sección de planes visible para cuentas con `plans.read`.
- Las cuentas con `plans.write` pueden registrar una oferta con nombre,
  velocidad, descripción, tarifa inicial, vigencia y motivo.
- Los cambios de tarifa se realizan mediante el endpoint especializado y
  preservan todos los periodos de precio.
- La interfaz impide ofrecer un cambio de tarifa el mismo día de creación,
  respetando que la nueva vigencia debe comenzar después de la actual.
- Desactivar un plan exige confirmación y motivo; sólo lo retira de nuevas
  altas.
- Los servicios existentes conservan plan y precio acordado después de cambiar
  o desactivar una oferta.
- El alta de servicios sigue mostrando únicamente planes activos con precio
  vigente.
- No se requirió migración de base de datos.
- Las ciento cuarenta y nueve pruebas permanecen aprobadas y Alembic confirma
  que no hay cambios de esquema pendientes.

## Módulo 34: cobertura y agenda de instalación desde la UI

- Se añadió la acción de evaluación para servicios pendientes y cuentas con
  `installations.write`.
- La cobertura puede registrarse como viable, con equipo especial o fuera de
  cobertura.
- El equipo especial exige descripción y los resultados viables exigen fecha
  programada.
- Una evaluación fuera de cobertura fuerza costo cero y no crea agenda ni
  cargo.
- Una instalación viable con costo genera su cargo mediante la regla
  autoritativa del backend.
- Antes de abrir el formulario, las cuentas con `installations.read` comprueban
  si ya existe trabajo programado para evitar duplicados.
- El módulo no permite completar ni activar el servicio; esas acciones
  conservarán pago, fotografías y navegación como requisitos independientes.
- No se requirió migración de base de datos.
- Las ciento cuarenta y nueve pruebas permanecen aprobadas y Alembic no detecta
  cambios pendientes.
