# Diario de desarrollo — 2026-07-31

## Módulo 38: operación diaria desde la UI

- Se revisaron primero los endpoints, el servicio de negocio y las pruebas ya
  existentes para no duplicar reglas en el navegador.
- Se confirmó que la API ya soportaba simulación y ejecución real mediante
  `/api/v1/operations/daily`.
- Se añadió una nueva vista operativa en `/app/` para consultar historial y
  disparar la operación diaria desde una fecha seleccionada.
- La pantalla separa explícitamente dos acciones: `Simular día` y
  `Ejecutar día`.
- La simulación no persiste registros, pero sí muestra el resultado esperado
  como resumen inmediato para el operador.
- La ejecución real inserta o reutiliza la corrida diaria idempotente del
  backend y actualiza el historial visible en pantalla.
- La navegación del módulo respeta capacidades: `operations.read` permite ver
  historial y `operations.run` habilita iniciar acciones.
- Se documentó el trabajo del módulo en esta bitácora para preparar el commit
  y la publicación posterior con contexto técnico claro.
- La validación enfocada quedó aprobada con `pytest` sobre frontend,
  operaciones diarias y autenticación.
- No se requirió migración de base de datos.

## Módulo 39: inventario y activos desde la UI

- Se reutilizó primero el backend existente de activos para evitar duplicar
  reglas de estado, propiedad y asignación.
- Se añadió una nueva vista de inventario con búsqueda rápida y filtro por
  estado operativo.
- La UI ya permite registrar activos nuevos con tipo, propiedad, identidad,
  fecha de adquisición y notas.
- Cada activo abre un detalle con resumen e historial de asignaciones.
- Si el activo está disponible o listo para reutilizar, la UI permite
  asignarlo a un servicio activo visible para el operador.
- Si el activo tiene una asignación activa, la UI permite registrar su
  devolución con resultado y condición de retorno.
- La interfaz mantiene separada la trazabilidad del activo del flujo de
  recuperación física, que sigue existiendo en la baja del servicio.
- Se actualizó la documentación y la prueba del shell frontend para respaldar
  el módulo antes del commit.

## Módulo 40: evidencia de mantenimiento con imágenes opcionales

- Se habilitó en la etapa de recuperación técnica un selector de archivos de
  imagen para adjuntar evidencia privada de forma directa.
- La captura de imágenes se diseñó como opcional: el técnico puede cerrar la
  tarea aunque no adjunte fotografías.
- Para evitar cargas accidentales grandes, la UI valida tipo de archivo
  imagen, máximo 6 archivos por visita y límite de 2 MB por imagen.
- La evidencia enviada al backend combina referencias manuales y adjuntos,
  manteniendo el límite total de 20 evidencias del contrato actual.
- Se añadieron pruebas de regresión para confirmar que la recuperación y la
  inspección de mantenimiento aceptan `evidence_references` vacías.
- Se incorporó una previsualización de miniaturas para validar imágenes de
  evidencia antes de cerrar la visita técnica.
